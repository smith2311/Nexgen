# Courier Auto-Fetch — Change Record

**Module:** Meril-V → Outbound Scanner → Finish Delivery
**Origin:** MOM 14 Sep 2026, item #13 (Mode of Transit)
**Status:** Code complete. Blocked on one business input — see §7.

---

## 1. Requirement

When a picker finishes a delivery, the Finish Delivery screen should fill in
the courier by itself — courier name, courier number, vehicle number, vehicle
type and Mode of Transit — so the picker confirms rather than types.

**Acceptance:** open Finish Delivery on a real delivery → courier fields are
already populated → Mode of Transit is already selected → picker only confirms.

---

## 2. Analysis

### 2.1 How auto-fetch decides

Three rules, most specific first. The first that matches wins.

| # | Rule | Reads from |
|---|---|---|
| 1 | A courier mapped to this exact customer | `CustomerCourierMapping` |
| 2 | The courier saved on the customer's record | `CustomerMaster.courier_partner` |
| 3 | The dispatching plant's default carrier | `CourierMaster.plant` |

### 2.2 What was actually wrong

Three separate faults, found in this order.

**(a) It filled in nothing at all.** Every one of the 25 deliveries in the two
real YVL06 dumps resolved to no courier.

**(b) When it did fire, it filled in only half.** Rules 1 and 2 store the
courier as a *name in a text box*, with no link to the Courier Master record.
The system therefore knew *which* courier but never opened its record — so
vehicle, vehicle type and Mode of Transit came back blank. Rule 3 was fine.

This made the failure look backwards: the *least* specific rule worked, and
the *most* specific one silently degraded Mode of Transit back to "Road".

A safety net was supposed to cover this on the browser side. It never ran —
the screen sets the courier box's value directly in code, which does not
trigger the handler that reads the courier list.

**(c) Migrated couriers would have arrived unusable.** The legacy importer
copied only name, number and vehicle number — it dropped **plant**, which is
the only thing rule 3 reads.

### 2.3 Root cause of (a) — verified, not assumed

Every possible source of courier data was checked against the real files.

| Source | Checked | Result |
|---|---|---|
| Customer extract | All **87** column headers read back from the stored source rows | **No courier column.** Searched for courier, forwarding agent, transporter, carrier, shipping agent, freight, logistics. Only matches were two delivery-*block* flags and "Shipping condition" (values `1`/`2` — an SAP service level, not a carrier) |
| YVL06 delivery dumps | All 30 / 28 headers | **No courier column.** Carries `Receiving plant` and `Shipping Point/Receiving Pt` — both hold the same value, so the plant is read correctly |
| Courier Master | Whole table | 8 rows, **all generated by `make_dummy_masters.py`** — sample data, not client data |
| Customer → courier mappings | Whole table | **0 rows** |
| Plant coverage | Courier plants vs delivery plants | Couriers sit on `CTN1, WAP1, WDL1, WGJ1–WGJ5`. Deliveries dispatch from **`9990`** and **`3044`**. **No overlap** |

**Conclusion: the courier data has never been supplied.** It is not a
column-naming mismatch and not a parser fault — there is nothing in any file
to read. Rules 1 and 2 cannot work at all on this data; **rule 3 is the only
one that can**, which makes `CourierMaster.plant` the single point of failure.

---

## 3. Design

| Decision | Why |
|---|---|
| Join the customer rules to Courier Master by **name** | The source files carry a courier *name*; `CourierMaster.id` exists only in the database and appears in no spreadsheet, so an import has nothing else to match on |
| Make the courier name **unique** (case-insensitive) | A name can only be a join key if it identifies one row. Both import paths already enforced this; the database now does too |
| Add **real foreign keys**, resolved on save | Reads get true referential integrity; imports keep working on the names |
| **Keep the name and code columns** beside the FKs | A row may legitimately name a party the master does not have yet — customer `P3092` carries all 24 MLSIPL deliveries and is absent from Customer Master. A required FK would make those rows impossible to create |
| Treat a **retired** courier as no courier | The FK survives deactivation; a withdrawn carrier must stop auto-filling |
| Make the data gap **visible** | It failed silently, which read as broken software. A plant with no carrier is now reportable |

## 4. Implementation

| # | Change | File |
|---|---|---|
| 1 | Customer-rule couriers now resolve their Courier Master row — vehicle, type and mode carried through | `merilv/views.py` |
| 2 | Courier name made unique, case-insensitively | `merilv/models.py` |
| 3 | Three foreign keys added — customer→courier, mapping→courier, mapping→customer — backfilled and kept in step on save | `merilv/models.py`, migration `0006` |

| 5 | Legacy courier import now carries **plant**, vehicle type, GSTIN and default mode | `merilv/services/legacy_import.py` |
| 6 | New readiness report + pre-filled upload template | `merilv/management/commands/courier_coverage.py` |

No change to the export format. No change to any other module.

## 7. Outstanding — business input required

**Everything above is done. Auto-fetch still fills in nothing, because no
carrier has been assigned to the plants that actually dispatch.**

This cannot be resolved in code. Someone who owns the data must say which
carrier serves which plant.

### How to close it

**Step 1 — see the gap.**

```
python manage.py courier_coverage
```

```
PLANT     DELIVERY LINES  COURIER        NAME
------------------------------------------------------------------
9990      126             — none —       ACADEMY WAREHOUSE

0 of 1 plant(s) can auto-fetch a courier.
```

**Step 2 — generate the template**, pre-filled with the plants in use and the
exact headers the upload screen expects.

```
python manage.py courier_coverage --template couriers.xlsx
```

**Step 3 — fill in the carrier.** Only two columns are required:

| Column | Required | Notes |
|---|---|---|
| Courier Name | **Yes** | The carrier. Must be unique — the customer links resolve by it |
| Plant | **Yes** | Already filled in |
| Courier Number, Vehicle Number, Vehicle Type, GSTIN | No | Auto-fill the matching boxes when supplied |
| Active | No | Blank counts as Yes |

**Step 4 — upload** on *Meril-V → Masters → Courier*. Re-uploading updates
rows in place; it never duplicates them.

**Step 5 — confirm.** Re-run `courier_coverage`; every plant should read as
covered. Open Finish Delivery on a real delivery: courier, number, vehicle,
type and Mode of Transit fill themselves in.

### Worth asking first

`make_dummy_masters.py` notes that its carrier list came from *"the original
customer file"* — so an **earlier** customer extract did carry a courier
column. Re-running the SAP customer extract **including the forwarding-agent
field** would populate rules 1 and 2 for all 7,480 customers at once, which is
far less work than building the plant list by hand.
